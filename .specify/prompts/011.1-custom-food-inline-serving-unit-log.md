# Plan: Custom Food Inline Serving Unit in Food Log Modal

## Context

Custom foods store their serving info inline in the `foods` table (`servingQty`, `servingUnit`, `servingWeightGrams`), unlike FatSecret foods which use the `food_alt_measures` table. The `/api/foods/detail` endpoint only builds the `servings` array from `food_alt_measures`, so it returns `servings: []` for custom foods. As a result, `FoodModal.buildFoodMeasures()` only offers the base "100 g" option — the user-defined serving unit (e.g. "1 scoop") is never presented.

## Approach

Synthesize a serving entry in the detail API from the custom food's inline fields, and handle its synthetic ID in the modal submit path.

### Two-file fix

**1. `src/app/api/foods/detail/route.ts`**

After collecting `altMeasures`, check if the food is `user_custom` with inline serving data. If so, prepend a synthetic `FoodServing` entry to the servings array:

```typescript
const customServing: FoodServing[] = [];
if (food.source === 'user_custom' && food.servingWeightGrams && food.servingUnit) {
  const w = parseFloat(food.servingWeightGrams);
  const qty = food.servingQty ? parseFloat(food.servingQty) : 1;
  const label = qty !== 1 ? `${qty} ${food.servingUnit}` : food.servingUnit;
  customServing.push({
    id: 'custom-serving',
    description: label,        // e.g. "scoop" or "2 scoops"
    weightGrams: w,
    calories: round(baseCalories * (w / 100)),
    protein: round(baseProtein * (w / 100)),
    carbs: round(baseCarbs * (w / 100)),
    fat: round(baseFat * (w / 100)),
    fiber: calcPer(baseFiber, w),
    sugar: calcPer(baseSugar, w),
    sodium: calcPer(baseSodium, w),
  });
}
```

Then in the response: `servings: [...customServing, ...altMeasures.map(...)]`

This ensures the custom serving appears first (becomes the default selection in the modal).

**2. `src/components/food-modal.tsx`**

In `buildFoodMeasures()`, map `custom-serving` id entries with `defaultQty` derived from the food's `servingQty`. Since the synthetic serving already has the right `weightGrams`, the existing `defaultQty: 1` for alt measures is fine — 1 scoop × 30 g/scoop = 30 g.

In the submit handler (log-food and edit-food modes), the line:
```typescript
const altMeasureId = selectedMeasureId === 'base' ? null : selectedMeasureId;
```
must be changed to:
```typescript
const altMeasureId = selectedMeasureId === 'base' || selectedMeasureId === 'custom-serving' ? null : selectedMeasureId;
```
This keeps the grams calculation correct (quantity × weightGrams) while not attempting to store a non-UUID as `altMeasureId` in the food log.

## Critical Files

- `src/app/api/foods/detail/route.ts` — add `customServing` synthesis before response (lines 124–138)
- `src/components/food-modal.tsx` — update `buildFoodMeasures` (line 41) and submit handler altMeasureId logic

2. Open the food log modal for that food — the serving dropdown should default to "scoop" (not "g").
3. Log it; confirm the food log stores the correct grams (e.g. 1 scoop = 30g).
4. Edit the log entry — modal should re-open with "scoop" selected.
5. FatSecret foods should be unaffected (their `source` ≠ `'user_custom'`, so `customServing` stays empty).
